# Durable school imports

The staff workspace submits one typed CSV/XLSX table per file. A batch owns the academic year, optional enrollment effective date and `defaultOnExisting` (`M` by default). Files have no conflict setting. A row's `on_existing` accepts trimmed, case-insensitive `S`, `M` or `O`; blank inherits the batch setting. Settings changes invalidate confirmation.

## Visible identifier contract

The required school identity rules are owned by [feature architecture §5.4.1](../../../edaya_frontend/docs/specs/feature-architecture-spec.md#541-visible-identifiers); the [durable-import contract](../../../edaya_frontend/docs/specs/feature-architecture-spec.md#durable-imports) owns template and matching behavior. These are specification requirements for the coordinated implementation, not evidence that current handlers or database migrations already satisfy them.

Human profiles accept an optional manual `identifier`. Blank values persist as NULL. Supplied identifiers use 1–20 ASCII letters/digits with single internal hyphens, NFKC normalization, trim and ASCII uppercase. Preserve leading zeros. Enforce uniqueness across years within each school and human group. Students also accept an independent optional `globalIdentifier` for external identification. Creation retries use a stable request identity.

Named non-human entities use `name` and `shortName`, with their existing internal `id` as stable identity. No third business `identifier` or identification `code` is added. Short names are non-unique UI text of 1–32 grapheme clusters, allowing accents, spaces and punctuation while excluding controls/line breaks. NFC/trim/whitespace normalization preserves case. Blank creation values receive a visible curated or full-name-derived suggestion without slugification or collision suffixes. Display edits never regenerate IDs or change relationships/source mappings. Non-human names/short names have no uniqueness or retirement mechanism; existing domain constraints unrelated to identity remain applicable.

Version 2 human files use `identifier` and student `global_identifier`; non-human files use `name`/`short_name`. Update-ready exports prefill `target_id`, and relationship exports prefill typed internal `*_id` references. Documented `_..._label` columns provide informational context and are not assertions against current names. Human relationship lookup accepts scoped `*_identifier` or exact internal IDs. Non-human relationships accept typed `*_name`/`*_short_name` lookup or exact internal IDs within the complete entity/parent/year scope in the owning contract. Text equality uses NFC, trimmed/collapsed whitespace and Unicode default case folding, retaining accents/punctuation; no fuzzy matching or scope widening. ID and non-informational text references must agree when both are supplied.

Reference lookup includes persisted and staged records, deduplicated by internal ID. Zero candidates is unresolved; one resolves; multiple require explicit user selection of an authorized candidate or file correction with an internal ID. Candidate responses expose only authorized names, short names and parent context; restricted matches cannot produce a false unique result or reveal hidden identities/counts. Preview resolution is a required server-authoritative command capability, bound to row/reference field, source revision, scope and reviewed internal target. Source evidence remains intact. Changing inputs or scope invalidates resolution. Confirmation freezes resolved IDs; execution rechecks authority, existence, scope and eligibility and never silently switches to another name match. A display-only rename does not retarget an already bound reference.

Reference resolution never implies selection of the row's update target. Non-human updates require `target_id`, an established source mapping, or explicit user selection of a target recorded as an internal-ID binding. A name/short-name match alone never updates or merges records. New non-human rows need only required business fields; the server assigns a stable staged identity. Existing/staged display-name matches require an explicit Create new or Select update target decision before execution. Human targets may also match their unique school/group identifier, with supplied keys and source bindings required to agree. Own-row name/short-name values are proposed edits after target selection, not identity assertions. S/M/O applies only after target determination and never changes internal IDs or human identifiers.

New humans accept a blank identifier. Supply a stable `source_id` to identify them across batches. Non-human source IDs are optional for initial creation but provide reliable cross-batch binding; otherwise retain exported target/reference IDs for later updates. One school/import-kind source mapping identifies one logical entity across batches; new annual entities require different source IDs. Provisional mappings and assigned IDs survive correction/retry and bind atomically with the business write. Duplicate update targets or conflicting source identities block; distinct new non-human records may share display text after explicit creation review. Original cells, source provenance and committed receipts remain intact. Obsolete headers receive correction guidance and block; old confirmed batches are never silently reinterpreted under version 2.

Database format checks and school/group unique indexes protect concurrent writes. An authorized correction checks the current value atomically and audits assignment, replacement or clearing. Released values may be reused. Archived profiles retain their values. Imports preserve existing identifiers on blank input and resolve updates through current identifiers, internal IDs or established bindings.

## Ports and dependency direction

`@edaya/service` depends on `@edaya/authorization`, which depends on `@edaya/core`. Core defines versioned templates, cells, update rules, import states, persistence and format ports. Authorization constrains admission, candidate visibility and current target access. The service stages, matches, previews, plans dependencies and invokes named school workflows. `@edaya/adaptor-postgres` persists batches, immutable file revisions, crosswalks, rows and immutable outcomes in the caller transaction. `@edaya/adaptor-import-format` owns ExcelJS and bounded CSV/XLSX decoding and serialization. It never calls a workflow. API composition supplies adapters; HTTP and scheduled dispatch use the same service.

The repository boundary checker rejects infrastructure, spreadsheet, HTTP, application and tooling imports in domain source and workflow imports in the format adapter. Application port tests run without SQL, HTTP or spreadsheet libraries; Postgres-backed workflow tests separately exercise atomic persistence and replay.

## Execution and correction

Validation freezes current and proposed business projections. Confirmation binds the revision, digest and effective modes and journals reference-only durable work. Each bounded page renews its lease, re-resolves the initiating human profile and current permissions, and invokes domain writes under the shared transaction locks. Row outcomes, identity mappings and requested enrollment/annual/relationship writes commit together. Stable operation receipts protect retries and lost responses. Capacity checks consider the complete net-new cohort and block every affected placement when over capacity.

Prerequisites run before their dependents. Unrelated ready rows proceed. Cancellation stops pending work and preserves completed records. Scheduled recovery resumes unfinished pages. Exhausted durable work is reported as failed and requires revalidation and confirmation. No tokens are stored. Original files are retained by the private-file lifecycle; logs and work payloads contain safe codes and references.

Corrections retain `row_id`, optional explicit `target_id`, source provenance and `on_existing`. Replacing a file creates an immutable revision. Successful unchanged logical operations retain their outcomes. Changing an already bound identity is a review conflict. Names, shared phone numbers and global identifiers never silently merge people.

`M` applies nonblank scalar values (including false and zero) and merges collections. `O` clears blank nullable mapped fields but preserves absent columns. A partial relationship file never deletes unmentioned members. Complete replacement requires an explicit owner-level `complete_collection` declaration and executes the entire owner group atomically. Posted payments and accepted billing terms require financial correction workflows for conflicts.

## Formats and release

The version 2 identifier contract covers the same import types: classes, subjects, students, guardians, teachers, staff, teacher assignments, chapters, billing, payments, academic disciplines, placement statuses, guardian relationships and class offerings. Annual student/teacher values belong to the selected year. Teacher declarations do not create assignments. Imports do not activate accounts or send invitations.

Limits: 5 MiB per file, 10,000 rows per batch, 128 columns, 32,768 characters per cell, one populated workbook sheet, 32 MiB expanded workbook, 8 MiB per ZIP entry, 500 ZIP entries. Formulas, encrypted workbooks, malformed dates, duplicate normalized headers and unsupported nonblank columns fail validation. `.xls` and irregular workbook preparation remain outside the application.

Apply additive migration `0047_durable_school_imports.sql` after the updated school model, regenerate web/mobile clients from the same backend candidate, qualify and run preview-only checks on externally prepared school files before approving a live batch. This change does not run the live intake.

The synthetic submission fixture accounts for 1,144 students, 27 classes, 34 teachers, 231 repeating/913 non-repeating values, 32 numeric workloads totaling 649 hours and two unknown workloads. All 156 coefficient cells and 12 totals have explicit pending-review dispositions, including three inconsistent totals. Pending evidence is never counted as an operational import.

Birth dates must be valid, unambiguous ISO dates and cannot be in the future. Ages below three or above eighty receive a nonblocking `IMPORT_BIRTH_DATE_REVIEW` warning for external review. Guardian rows contain `phone`, `alternative_phone`, `email`, `email_notifications_enabled`, `sms_notifications_enabled` and `push_notifications_enabled`. Contact fields follow scalar merge/overwrite rules; omitted switches preserve saved preferences. New guardians default to enabled channel preferences. The former guardian-contacts format and contact collection columns are unsupported.

Confirmation drains bounded pages through the durable dispatcher (20 seconds on Workers; five minutes locally). The deployed heartbeat runs every five minutes and recovers remaining or interrupted work. The local API runs a non-overlapping recovery drain at startup and every minute, using the same runtime and honoring local job pauses. Page/elapsed limits stop between row transactions and leave persisted continuations; they never depend on browser polling.

Phone imports accept a leading `#` as an Excel-friendly alternative to `+`. The service normalizes scalar phone fields, including guardian alternative phones, while preserving raw cells and other fields. Guardian contact validation then normalizes spacing, punctuation and international prefixes and rejects duplicate main/alternative numbers. Matching never uses the phone alone.

Guardians may have an empty first name with a required nonblank last name. No name components are inferred. For existing records, blank first names preserve in M and clear to the empty string in O; omitted columns preserve in every mode. Student and teacher first names remain required.

## Execution and progress reads

The executor fetches at most ten ready candidates and revalidates each under the existing command/academic/permission locks. It loads only the current row and complete-collection members; complete collections remain atomic even when larger than a page. Capacity checks include every pending admission to the affected class, so an oversubscribed cohort is blocked together. Matching uses school-scoped predicates and current access scopes. Compulsory participation remains the placement domain hook's responsibility, with related context and invalidation evidence shared within that placement transaction.

Human business-key matching and non-human readable reference lookup use their distinct normalization rules from the owning contract, with ambiguity detection and restricted-candidate handling. Once references are resolved, target matching uses exact technical IDs, including academic-year and foreign-key IDs. Preview validation shares authorization facts and readable entities only within its read-only preflight context; subsequent previews, confirmation and execution re-evaluate current authority. Execution contexts do not retain these preflight caches across collection writes. Student, guardian, teacher and human-staff save gates query scoped identifier-conflict candidates rather than loading every person in the school. Human import matching and ordinary saves use the same equivalence rule; database uniqueness enforces the canonical human value. Non-human text matching resolves references only and establishes no name/short-name uniqueness requirement.

Submission loads existing source identities in groups of 200 and persists pending identities in bounded groups. Repeated source IDs within the file share the pending identity and remain subject to duplicate-target validation. Preview loads receipt outcomes by row ID and input digest in groups of 200; unchanged successful operations keep their original operation ID and result. Execution reuses the current transaction's row for non-collection commands and shares preflight facts only until the first business write. Each collection member's write receives a fresh execution context. Guardian linking returns the scoped records from one read-only authorization preflight, while entity persistence retains fresh write authorization.

For new placements, the shared compulsory-participation workflow validates every selection before batching selection writes and offering revision updates in groups of 500. Dependency checks and assessment/report invalidation still use the existing per-selection rules, within the same academic-state transaction. Failed writes roll back the entire placement; each changed selection still increments its offering revision. This optimization does not make compulsory participation an import responsibility.

Migration `0050_import_progress.sql` adds execution indexes and backfills progress metadata without changing approval or receipt identity. Row persistence updates outcome and numeric-result counters, progress version and timestamp in the same transaction. Identical saves and command receipt replay do not increment them. The `imports.status` response contains batch, counts, version and updatedAt; it does not contain source rows. Status, history and detail share current visibility checks, performed in bounded entity queries. Detail reads no longer repair jobs; the dispatcher reconciles exhausted work independently of readers.

The local API invokes the existing dispatcher at startup and every minute using its own database runtime. Local drains do not overlap, honor PAUSE_SCHEDULER and PAUSE_JOBS, and finish before runtime shutdown. Durable leases coordinate request-triggered drains and restart recovery. No separate PGlite process is launched. Deploy the additive migration with the matching backend and regenerate clients before enabling status polling.
