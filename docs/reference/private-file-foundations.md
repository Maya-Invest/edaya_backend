# Private file foundations

Plan 00 extends the existing file storage port; photo review, branding, document issuance and survey retention remain owned by their feature plans. Persisted upload admission, immutable completion, scoped downloads, bounded asset reads and reference-safe cleanup are implemented. Purpose restrictions now extend the same scoped repository predicates; command journal adoption and the overall Plan 00 exit gate remain outstanding.

## Bounded object reads

`FileStoragePort.readObject(key, { maxBytes })` reads a complete object from the configured private store. `maxBytes` is a required positive integer, at most 25 MiB. This is an application memory ceiling, not an R2 object limit. Feature capabilities must choose a narrower limit appropriate to each asset and bound the number of assets loaded together.

The result contains owned `Uint8Array` bytes, actual `sizeBytes`, content type and optional ETag. Missing objects return `null`. Invalid limits, excess bytes and transport failures use `FILE_READ_LIMIT_INVALID`, `FILE_READ_LIMIT_EXCEEDED` and `FILE_READ_FAILED`. Network errors do not include signed URLs, credentials or provider response text.

The stream reader checks actual accumulated bytes, even when the declared length is absent or too small. It cancels on overflow/failure and releases its reader. Successful memory reads return copies. Stream assembly can temporarily retain both the bounded chunks and their combined result; the limit is per complete object, not a total process-memory guarantee. This interface does not itself provide content signature validation, a download deadline or an aggregate render budget.

R2 uses `GetObject` against the configured endpoint/bucket and persisted object key. It never follows a supplied asset URL or mints a public URL to retrieve bytes. The implementation uses the existing AWS SDK and its stream conversion. See [R2 S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/) and [AWS GetObject](https://docs.aws.amazon.com/AWSJavaScriptSDK/v3/latest/client/s3/command/GetObjectCommand/). No SDK or provider migration is required.

The local file service provides an authenticated internal content route with a mandatory bound. Its disk reader streams bytes, so an object larger than its metadata cannot bypass the limit. The HTTP client rejects redirects and bounds the received body independently. Memory and API development disk adapters implement the same port. Development disk keys now use the existing storage-root path validation.

## Authorized attachment assets

`loadAttachmentAsset(baseService, request)` accepts an attachment ID, expected owner kind/ID, allowed MIME types and byte limit. The consuming capability supplies these constraints from its authoritative business resource and narrower purpose policy; they are not raw client-selected storage authority.

The loader obtains the record through the current actor's scoped attachment repository before reading storage. It requires the selected school, expected owner, ready state, private storage key and permitted metadata. It rejects legacy `fileUrl`-only attachments. After a successful storage call it repeats the scoped read and compares the record, withholding bytes when access was revoked or the record changed. Actual size and content type must match the attachment. Missing objects do not bypass this final authorization check; storage errors reject the operation without returning bytes.

Call this loader outside a business transaction. The native PostgreSQL test demonstrates that storage I/O can borrow the same pool's only connection and that revocation during I/O prevents returned bytes. Features with a subsequent write must reauthorize their transition inside its transaction. The loader creates no receipt, audit or outbox record because it is an internal read, and it exposes no public endpoint or generated DTO.

Plan 00 supplies the shared purpose-policy extension points described below. Plan 02 supplies approved portrait/branding references and its narrower feature rules. Plan 04 connects the loader to all document assets and supplies a bounded aggregate render budget; renderers must receive validated bytes rather than arbitrary image URLs. The loader verifies current metadata and bytes. New uploads obtain their ready record through the completion protocol below; historical ready records remain subject to their feature migration and content qualification.

## Purpose-scoped metadata, uploads and delivery

Migration `0019_attachment_purposes` adds a non-null purpose with `general` as the legacy default. Existing attachment content/owner fields are preserved. Purpose identifiers are bounded lowercase identifiers; a database constraint rejects invalid values and a trigger rejects changing an existing purpose. Publish a feature reference to the same protected artifact or create a new admitted artifact; do not declassify an attachment by changing its purpose.

`ResourceAccessClause.attachmentPurposes` contains exact values chosen by the policy. `resourceAccessScope` defaults omitted purpose selections to `general` for attachments and copies/freezes the selection. An explicit empty selection denies everything. The SQL compiler combines each purpose selection with that clause's school, owner, relationship and publication predicates before reads, lists, counts and pagination. Generic attachment actions, including school-wide owner/staff authority, reach only `general`. An unknown purpose is concealed through those actions. A purpose is a restriction, never a substitute for permission or current owner access.

Future capabilities supply named authorization policies through two internal typed hooks; these callbacks are never deserialized from HTTP or stored as client authority:

- `AttachmentUploadPolicy` fixes `purpose` and provides `assertSave(attachment, existing)`. Admission and every later phase call it again, check the scope's school/resource, apply its SQL predicate to existing/proposed attachments and validate owner school. It must authorize the feature action, current actor/relationship, source lifecycle and both targets. The current generic upload route accepts no caller-selected purpose, and direct generic service input rejects that field. Intent purpose is server-fixed and completion must match it. Generic completion/replay cannot use a feature-purpose intent.
- `AttachmentReadPolicy` fixes `purpose` and provides `readScope()`. `loadAttachmentAsset` accepts it as `request.access`; `grantAttachmentDownload` accepts it as `options.access`. Both reload the policy before storage and after successful I/O, retain school/owner/type/size checks, and withhold results after revocation or metadata change. Feature-specific downloads require a private key; they never convert a historical external URL into a bounded grant.

Feature policy callbacks return the existing `ResourceAccessScope`, with exact purpose and business resource constraints. They remain in `@edaya/authorization`; feature services pass their named policies to the shared I/O helpers. There is no runtime permission registry, new generic approval engine or client-selected policy. Plans 02/04/05 supply their actual audiences/lifecycles and projection rules; the shared tests use a synthetic purpose solely to verify the extension contract.

The public attachment response includes `purpose`. Generic `registerAttachment` requests may omit it for the backward-compatible `general` default; supplying a different purpose cannot alter the persisted admission. Regenerated TypeScript/Dart contracts retain existing callers. Read tests cover staff, teacher, guardian and student profiles sharing one login, unknown purposes, current revocation, foreign school/child, REST counts, private download concealment and the one-connection native path.

## Persisted uploads and completion

`createAttachmentUpload(base, input)` retains the existing upload-intent API result. It fixes school and caller identity from the authenticated actor, validates the current owner and write permission in a transaction, and persists a pending intent before signing. Migration `0017_attachment_uploads` stores this private intent separately from public attachment rows. Its constraints bind school, attachment ID and pending metadata; writes require the current transaction. Database failures use a fixed code rather than logging query parameters or staging credentials.

An optional client attachment ID identifies a retry. Reissuing the same caller/metadata returns the original staging key without extending its fifteen-minute expiry. Another caller, changed metadata, expiry or a completed intent cannot open a replacement upload. Metadata must be nonempty and have no surrounding whitespace. The intent records owner, MIME type, exact positive size, server creation time and uploader. Generic attachment saves/batches cannot publish ready rows. The public registry is command-only: REST omits generic attachment mutations and regenerated clients reject them before network access.

`completeAttachmentUpload(base, input)`, used by the existing `registerAttachment` command, matches input to the persisted intent, reads bounded actual bytes outside SQL, checks byte count and MIME metadata, identifies the content signature, and hashes the accepted bytes with SHA-256. It copies them to a server-selected accepted key before a final authorized transaction publishes the ready attachment and records completion together. The accepted key includes attachment identity and the byte digest; temporary upload credentials cannot modify it. Concurrent completions converge on the committed result, and replay returns the current authorized record without trusting a subsequently overwritten staging object. Caller-supplied uploader/time cannot override server metadata; external URLs, checksums, substituted owners and fabricated readiness cannot authorize completion.

Content identification uses pinned `file-type@21.3.4`, through its bounded-buffer `file-type/core` entry. This is signature/type validation, not complete format decoding or malware scanning. See the primary [file-type documentation](https://github.com/sindresorhus/file-type). The supported matrix is JPEG, PNG, APNG, WebP, GIF, PDF and DOCX, subject to the existing owner-specific restrictions and byte ceilings. Real synthetic files exercise admission through immutable completion. APNG may be admitted as `image/png` or `image/apng`; ordinary PNG cannot impersonate APNG. Legacy DOC is rejected at admission because generic CFB detection cannot establish Word content. Arbitrary ZIP, MIME mismatch, unidentifiable data and tested truncated content fail closed. Byte counts must be positive safe integers within the owner limit. No client-specific DOC allowlist was found in current web/mobile source. Plan 02 additionally owns decoded image and dimension policies.

The local API PUT adapter accepts only an unexpired random staging capability from this store and enforces exact actual byte count. Its errors use stable size/type codes. Local HTTP storage signs the admitted size and enforces it while streaming; R2 signing includes Content-Length. Completion enforces the bound independently for every provider. The R2 signed-header unit assertion is not deployed browser/R2 qualification. Provider reads, writes and signing remain outside business transactions; the native test borrows a pool's only connection during these calls.

Upload admission and completion now emit reference-only command receipts and minimal audit facts atomically with their database effects. Lost upload-URL recovery reloads the secure intent and reauthorizes before signing outside SQL; neither URL nor storage key is stored in the receipt. Completion replay returns only the original unchanged authorized attachment. See the [file command contract](command-execution.md#file-command-adoption). Migration `0018_private_file_lifecycle` now inventories staging and accepted keys before I/O. Copied but unpublished objects can remain temporarily after failure; the cleanup protocol below makes them eligible after their protection window.

## Private delivery and compatibility

`grantAttachmentDownload(base, attachmentId, options)` scopes the metadata read before loading a record, requires readiness, asks the configured store for a fifteen-minute grant, and rechecks current access and unchanged metadata after signing. Provider failures are sanitized. Public content/download routes use this helper and private/no-store responses. The API memory GET requires authentication and the bounded, reauthorized asset loader; an object key alone cannot read accepted content.

The HTTP logger excludes authorization and response headers, signed Location values and the local staging path. The application can revoke subsequent grants; an already issued storage URL remains usable until its bounded expiry. Historical `fileUrl`-only records return no grant. Both private delivery endpoints return the existing concealed 404 without a Location header or copied external URL. The server cannot enforce expiry on an external link, so it never labels that link as signed delivery. Metadata remains intact for the owning migration; there is no arbitrary remote fetch, automatic import or destructive rewrite. Records with a private storage key continue through scoped signing and current reauthorization, including historical records that also contain an external alias.

Before release, Plans 02/04 must inventory and replace external-only references that are expected to remain downloadable, using admitted uploads and verified private references. A legacy attachment reached through a canonical content URL is unavailable until that replacement succeeds. Existing private portraits and artifacts remain readable under their current policies. Direct external profile/branding URLs are separate feature projections; this change does not pretend to revoke or privatize copies already hosted externally.

Mutation seeds now use admitted uploads and completion for both profile images and generic attachments. Declarative fixture selection remains separate from orchestration; attachment bodies use checked-in synthetic PDF/JPEG assets and actual byte sizes. Existing ready deterministic seed identities are reused for reruns.

## Object inventory, references and cleanup

Migration `0018_private_file_lifecycle` adds school-bound `private_file_objects` and `private_file_references`. These are internal persistence ports, not generic public entities. The migration backfills existing attachment keys and canonical profile-photo references without changing their business fields. Dangling canonical attachment URLs must be repaired before applying the migration; reference protection does not silently discard them.

`PrivateFileLifecycleStore.reserve` runs in a transaction before external writes. Upload staging keys remain protected through the fifteen-minute admission expiry plus one hour; accepted copies and report PDFs receive a one-hour write window. Logbook exports reserve before upload and extend protection around their fifteen-minute download grant. Referenced objects remain protected beyond the window. The object state is `reserved` while references may be created, then `deleting` and `deleted`; these states are separate from an attachment's upload/readiness state.

Database triggers maintain attachment storage references and photo links for staff, teachers, students and guardians. Canonical `/core/files/{id}/content` links protect attachment metadata through a foreign key. Encoded direct storage URLs also retain their object. Reference writes check school and object state under the same key-family lock used by cleanup. `privateFiles.retain` and `release` let future authorized capabilities maintain `capability.<name>` source/slot references in their business transaction; they cannot overwrite native reference namespaces. The caller must authorize its source and lifecycle transition. These methods confer no public authority.

`removeAttachment` rechecks the scoped existing record and configure action, locks its metadata, rejects retained attachment links, deletes the metadata and persists cleanup eligibility in the same transaction. Its receipt, minimal removal audit and cleanup eligibility commit with metadata deletion. Replay reauthorizes the original owner and refuses an ID occupied by a replacement. It performs no storage I/O. Current failures include `ATTACHMENT_REFERENCED`, concealed missing/inaccessible records and `ATTACHMENT_LEGACY_ALIAS` for a private key with an opaque historical external URL. That alias requires its owning feature's migration before removal. Provider and new database-constraint diagnostics are sanitized rather than exposing private URL parameters.

The existing scheduler runs `preparePrivateFileCleanup` every fifteen minutes. Its named integration policy admits only cleanup identities and fixes the school. A batch considers at most fifty due objects and reloads references before tombstoning each key. Tombstone, minimal audit and reference-only outbox work commit together through `CommandExecution`. Concurrent schedulers cannot publish two cleanup jobs for the same generation.

API heartbeats dispatch `private-file.cleanup` through the existing durable-work store after cron transactions. The worker validates version, school, object ID and the current bound job ID, then calls storage outside SQL. It records completion in a short transaction. Leases, interruption recovery, eight-attempt retry budgets and terminal failure states come from the shared work adapter. Provider failures persist only `PRIVATE_FILE_STORAGE_UNAVAILABLE`. Missing objects are an idempotent success; local filesystem failures other than ENOENT now remain failures. No exactly-once network deletion is claimed.

Deleted keys stay tombstoned and cannot be republished or renewed. Daily bounded sweeps revisit them to remove a late write from an already-issued upload capability; they never make that object publishable again. A dead cleanup job leaves the tombstone in place for operational inspection. Feature retention decisions remain with Plans 02/04/05.

Legacy safety is deliberately explicit. Imported metadata is retained until detached. Ambiguous local disk key families (sidecar suffixes, path spelling, Unicode and case aliases) are held instead of risking a referenced artifact; new write reservations serialize and reject such aliases. Objects that ever had an opaque external alias are retained for the owning feature's migration. Cleanup does not scan arbitrary bucket keys or infer ownership of historical objects lacking an inventory record. Every current upload, report-card write and logbook export now reserves its key before storage I/O.

## Transaction boundary verification

Current notification/invitation enqueue, cancel and revoke operations write persistence only; provider dispatch runs after commit. Notification identity contact resolution also runs after its scoped database phase. Template rendering is in process. Upload signing/reads/copies, bounded attachment reads, download signing, report rendering/storage, logbook rendering/storage/signing and private-object deletion run outside business transactions. Native tests borrow the same pool's only connection during these external calls; competing-worker and rollback tests verify the database phases. Call these orchestration functions outside an enclosing business transaction.
