# Better Auth integration plan

> **Note:** Auth persistence now lives in `package/integration-betterauth-d1-migrations` (`@edaya/betterauth-d1-migrations`), not `packages/adaptor-betterauth`. See [integrations restructure](../../docs/integrations-restructure.md).

Complete the API-side Better Auth integration so a real email/password sign-in produces a session, resolves to an `ActorMetadata`, and authorizes core routes. **Webapp work is explicitly out of scope.**

**Related docs:** [API runtimes](../../docs/api-runtimes.md), [Authorization README](../../package/domain-core/src/authorization/README.md), [Webapp integration plan](./webapp-api-integration-plan.md) (Phase 1 deferred).

---

## 1. Goals and non-goals

### Goals

| # | Outcome |
|---|---------|
| G1 | Better Auth tables exist in Postgres/PGlite via versioned Drizzle migrations |
| G2 | `apps/api` uses a shared Drizzle schema when configuring `drizzleAdapter` |
| G3 | Dev seed creates sign-in-able users linked to staff/guardian/student records (`subjectId`) |
| G4 | Integration test proves: sign-up → sign-in → cookie → protected route → resolved actor |
| G5 | Auth migrations run automatically in dev/test alongside school migrations |

### Non-goals (this iteration)

- Webapp login UI or Better Auth browser SDK
- OAuth / social providers
- Email verification, password reset, MFA
- Assurance-level elevation (`verified` / `strong`) beyond default `standard`
- CORS changes for direct browser → API auth

## 2. Current state

```
apps/api
  create-auth.ts          → betterAuth({ drizzleAdapter(db), emailAndPassword })
  auth.route.ts           → proxies /auth/* to auth.handler
  session-actor.ts        → getSession() → findOne({ subjectId }) → effectiveGrants

package/adaptor-postgres
  drizzle/                → school domain tables only (no user/session/account)
  repos.init()            → runs school migrations lazily

Gap: Better Auth has no schema. Dev seed creates domain entities without subjectId or auth users.
```

**Naming note:** the school table `sessions` is for **class sessions** (scheduling). Better Auth uses `session` (singular). No collision, but document this in the adaptor package README.

## 4. New package: `@edaya/adaptor-betterauth`

Mirror `package/adaptor-postgres` conventions (name uses **adaptor**, not adapter).

### 4.1 Package layout

```
packages/adaptor-betterauth/
  package.json
  tsconfig.json
  tsconfig.build.json
  drizzle.config.ts
  src/
    index.ts                    # public exports
    schema.ts                   # generated by @better-auth/cli
    lib/
      migrate.ts                # getMigrationsFolder + runMigrations (pglite | postgres-js)
    cli/
      auth-config.ts            # minimal betterAuth() instance for CLI schema generation only
  drizzle/
    0000_*.sql
    meta/
  README.md                     # table glossary, migration commands, naming collision note
```

### 4.2 Dependencies

| Package | Role |
|---------|------|
| `better-auth` | CLI generation + schema types |
| `drizzle-orm` | schema definitions |
| `drizzle-kit` (dev) | generate/apply migrations |

No dependency on `@edaya/core` — auth storage is infrastructure, not domain.

### 4.3 Schema generation workflow

1. Add `src/cli/auth-config.ts` — minimal config matching production plugins:

   ```ts
   betterAuth({
     database: drizzleAdapter(db, { provider: 'pg', schema }),
     emailAndPassword: { enabled: true },
   })
   ```

2. Add script to `package.json`:

   ```json
   "auth:generate-schema": "bunx @better-auth/cli@latest generate --config ./src/cli/auth-config.ts --output ./src/schema.ts --yes"
   ```

3. Run `drizzle-kit generate` → commit SQL + snapshot.

4. **Pass `schema` to `drizzleAdapter` at runtime** (required by Better Auth; see [drizzle adapter docs](https://www.better-auth.com/docs/adapters/drizzle)).

### 4.4 Public API

```ts
// packages/adaptor-betterauth/src/index.ts
export * as authSchema from './schema'
export { getMigrationsFolder, runMigrations } from './lib/migrate'
export type { MigrationDriver } from './lib/migrate'
```

### 4.5 Root workspace scripts

Extend root `package.json`:

```json
"db:generate:auth": "bun --filter @edaya/adaptor-betterauth db:generate",
"db:migrate:auth": "bun --filter @edaya/adaptor-betterauth db:migrate",
"auth:generate-schema": "bun --filter @edaya/adaptor-betterauth auth:generate-schema"
```

Keep school and auth migration commands **separate** — independent journals, independent lifecycles.

## 5. API wiring changes

### 5.1 `create-auth.ts`

```ts
import { authSchema } from '@edaya/adaptor-betterauth'
import { drizzleAdapter } from 'better-auth/adapters/drizzle'

export function createAuth(db: unknown, env: Environment): AuthService {
  return betterAuth({
    database: drizzleAdapter(db as never, {
      provider: 'pg',
      schema: authSchema,
    }),
    secret: env.BETTER_AUTH_SECRET,
    baseURL: env.BETTER_AUTH_URL,
    emailAndPassword: { enabled: true },
  }) as AuthService
}
```

### 5.2 Migration bootstrap in `createApiRuntime`

Run auth migrations **eagerly** before `createAuth()` (auth tables must exist before first request). School migrations can remain lazy in `repos.init()`.

```ts
const { db, sqlClient } = await createDatabase(env)
await runAuthMigrations(db, { driver: resolveMigrationDriver(env) })
const auth = createAuth(db, env)
```

Extract `resolveMigrationDriver(env)` to a small shared helper (or duplicate the `isEphemeralDatabase` check already in `create-runtime.ts`).

### 5.3 Integration test harness

Update `testing/integration-tests/src/support/suite-runner.ts` (or a new `describeAuthIntegration` helper) to:

1. Create PGlite + drizzle `db`
2. `runAuthMigrations(db, { driver: 'pglite' })`
3. `repos.init({ driver: 'pglite' })`
4. Instantiate `betterAuth` with the same `db` + `authSchema`

## 6. Identity linking (`subjectId`)

### 6.1 Contract

| Field | Meaning |
|-------|---------|
| `StaffMember.subjectId` | Better Auth `user.id` |
| `Guardian.subjectId` | Better Auth `user.id` |
| `Student.subjectId` | Better Auth `user.id` |

`session-actor.ts` already enforces:

- Exactly **one** domain identity per `subjectId`
- `actor: null` if zero or ambiguous matches

### 6.2 Linking strategies

| Context | Approach |
|---------|----------|
| **Dev seed** | After domain seed, call Better Auth sign-up API, then patch `subjectId` on entities via system actor |
| **Admin provisioning (later)** | New core command `linkActorSubject` — see Phase 3 |
| **Self-registration (later)** | Out of scope; would need invite tokens |

`registerStaffMember` command intentionally omits `subjectId` — linking is a separate, privileged step.

### 6.3 Dev auth seed (`runDevAuthSeed`)

New module: `apps/api/src/lib/seed/run-dev-auth-seed.ts`

| Step | Action |
|------|--------|
| 1 | Define `DEV_AUTH_ACCOUNTS` aligned with `SEED_STAFF` / `SEED_GUARDIANS` emails |
| 2 | For each account, call `auth.api.signUpEmail({ body: { email, password, name } })` (or equivalent server API) |
| 3 | Capture returned `user.id` |
| 4 | System actor saves `subjectId` on the matching staff/guardian/student record |
| 5 | Idempotent: skip if user already exists (check by email or if `subjectId` already set) |

**Dev credentials:** document in `apps/api/.env.example` (e.g. `DevPassword1!` for all seed accounts). Never use in production.

Extend `maybeSeedDatabase` signature or call `runDevAuthSeed` from `node.ts` entry after domain seed, passing `runtime.getAuth()`.

## 7. Phased delivery

### Phase 0 — Scaffold `@edaya/adaptor-betterauth` (1–2 days)

- [ ] Create package with tsconfig, tsup build, eslint
- [ ] Add `auth-config.ts` + `auth:generate-schema` script
- [ ] Generate `schema.ts`, run `drizzle-kit generate`, commit initial migration
- [ ] Implement `runMigrations` (copy pattern from `adaptor-postgres`)
- [ ] Add package README
- [ ] Register in root workspace + Turbo

**Done when:** `bun db:migrate:auth` against a local Postgres creates `user`, `session`, `account`, `verification` tables.

### Phase 1 — Wire API runtime (1 day)

- [ ] Add `@edaya/adaptor-betterauth` dependency to `apps/api`
- [ ] Update `create-auth.ts` to pass `schema`
- [ ] Run auth migrations in `createApiRuntime` before `createAuth`
- [ ] Verify manually: `POST /auth/sign-up/email` → `GET /auth/session` returns user
- [ ] Update `docs/api-runtimes.md` (remove stale `auth.config.ts` reference)

**Done when:** sign-up and sign-in work against pglite dev server without manual SQL.

### Phase 2 — Dev seed + identity linking (1–2 days)

- [ ] Add `runDevAuthSeed` with idempotent sign-up + `subjectId` linking
- [ ] Link at least: 2 staff (e.g. `st5`, `st1`), 1 guardian (`g1`)
- [ ] Log seed summary: emails + dev password hint
- [ ] Manual smoke: sign-in as `c.moreau@school.edu` → `GET /api/core/authorization/effective-grants` returns staff actor

**Done when:** seeded dev user gets non-null actor and grants on a protected route.

### Phase 3 — Core command for admin linking (1 day, optional but recommended)

- [ ] Add `linkActorSubject` workflow in `@edaya/core` (`setup` or new `access-control` workflow)
  - Input: `{ staffMemberId | guardianId | studentId, subjectId }`
  - Permission: `ACCESS_CONTROL_ASSIGN` (or `STAFF_UPDATE` for staff-only MVP)
  - Validates: entity exists, `subjectId` not already bound to another entity of same kind
- [ ] Register command in API registry + OpenAPI schema
- [ ] Unit test in `package/domain-core`

**Done when:** admin can link an existing Better Auth user to a staff record without system actor.

### Phase 4 — Integration tests (1–2 days)

- [ ] New suite: `testing/integration-tests/src/auth/better-auth-session.integration.test.ts`
- [ ] Test cases:
  - sign-up creates DB rows in auth tables
  - sign-in sets session cookie
  - Request with cookie → `session-actor` resolves staff actor
  - Unlinked `subjectId` → 401 on protected route
  - Ambiguous `subjectId` (staff + guardian same id) → 401
- [ ] Optional API-level test in `apps/api/tests/routes/` using real `betterAuth` instance (lighter than full integration suite)

**Done when:** `bun test` in integration-tests covers the full auth → actor path.

### Phase 5 — Production hardening (defer unless deploying soon)

- [ ] `trustedOrigins` when external clients are added
- [ ] `BETTER_AUTH_SECRET` rotation notes in runbook
- [ ] Worker runtime: confirm auth migrations run on cold start with `postgres-js` driver
- [ ] Rate limiting on `/auth/*` (Cloudflare or Hono middleware)

## 9. Risks and mitigations

| Risk | Mitigation |
|------|------------|
| Better Auth CLI schema drift on version bump | Pin `better-auth` version; re-run `auth:generate-schema` + diff in upgrade PRs |
| `drizzleAdapter` requires `schema` at runtime | Enforced in `create-auth.ts`; add failing test if schema import removed |
| Two migration journals on one DB | Document run order; both run in `createApiRuntime` / test harness |
| Dev seed creates weak passwords | Dev-only; document; gate behind `SEED_ON_START` / ephemeral DB |
| `subjectId` collision across entity types | Existing middleware returns `null` actor; add integration test |
| School `sessions` vs auth `session` confusion | README glossary in adaptor-betterauth |

## 11. Definition of done

Better Auth integration is **complete** (webapp excluded) when:

1. `@edaya/adaptor-betterauth` owns schema + migrations and is the single source of truth for auth tables
2. `bun dev` on pglite auto-migrates auth tables and seeds linkable users
3. `POST /auth/sign-in/email` + cookie → `GET /api/core/authorization/effective-grants` returns a staff actor with grants
4. Integration tests cover the sign-in → actor path
5. Admin can link subjects via `linkActorSubject` command (Phase 3) or documented system-actor workaround until then
